# Omarchy UI patterns Rashell should borrow

**Decision:** Borrow Omarchy's cohesive shell grammar—one warm runtime, a three-zone bar, anchored keyboard-accessible task panels, direct searchable routes, semantic theme tokens, and lightweight OSD/toast feedback—but not its distro management, app provisioning, Hyprland policy, or plugin marketplace.

## Scope and source basis

This review uses only Omarchy's official site and the authoritative first-party `basecamp/omarchy` repository, pinned at commit [`20400ba`](https://github.com/basecamp/omarchy/tree/20400badda3862b5d533cadcb20730720360934d). Omarchy describes itself as an opinionated Linux distribution, not merely a shell, and says its repository manual is authoritative ([official site](https://omarchy.org/), [README](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/README.md)). That distinction determines what transfers to standalone Quickshell software.

## Patterns actually present and the Rashell decision

### Borrow now

1. **One cohesive runtime with explicit surface roles.** Omarchy runs the bar, panels, overlays, menus, notifications, lock UI, and shared services in one long-running Quickshell process; commands and keybindings summon already-hosted surfaces through IPC. It distinguishes `bar-widget`, `bar`, `panel`, `overlay`, `menu`, and headless `service` composition roles ([shell architecture](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/docs/omarchy-shell.md)). Rashell should likewise have one shell-owned surface router and shared state/services. Use those roles as **internal typed boundaries**; a public extension platform is not required.

2. **A stable three-zone bar that reveals tasks, not just status.** Omarchy's default composition is menu/workspaces on the left, contextual status and a centered clock in the middle, and system controls on the right ([default layout](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/config/omarchy/shell.json)). `centerAnchor` keeps the clock geometrically centered while conditional widgets appear or disappear. Bar controls open real panels, and active modes appear as compact indicators while inactive ones stay out of the way ([top-bar manual](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/05-the-top-bar.md)). Rashell should borrow the stable center anchor, state-driven visibility, and bar-to-panel relationship. Drag-to-reorder, edge relocation, and full bar replacement can wait until fixed composition proves insufficient.

3. **Panels are compact task surfaces with mouse/keyboard parity.** Omarchy panels perform the task in place rather than acting as read-only popovers. Its audio surface combines master volume, output choice, input controls, and per-application mixing, and its source implements a shared cursor across sections with arrows or `j`/`k`, `h`/`l` adjustments, Enter/Space activation, and visibility based on available devices/streams ([audio manifest](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/shell/plugins/panels/audio/manifest.json), [audio panel source](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/shell/plugins/panels/audio/Panel.qml), [panel behavior](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/05-the-top-bar.md)). This fits Rashell directly: make its audio panel the first reference surface, with volume/mute, direct output/input selection, and later per-stream controls behind one consistent focus model.

4. **The same action is reachable by bar, direct hotkey, menu route, and command.** Omarchy is keyboard-first, but not keyboard-only: direct bindings open common panels, while the menu remains a searchable, hierarchical fallback ([hotkeys](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/07-hotkeys.md)). The menu is data-defined, supports direct routes to submenus/actions, filters as the user types, and uses one select/input surface for transient pickers ([menu design](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/docs/menu.md)). Rashell should define action IDs once and let bar controls, shell IPC, and Hyprland bindings invoke them. Add a compact searchable command surface only when there are enough actions to justify it; do not duplicate action logic in each entry point.

5. **Semantic visual tokens, including interaction states.** Omarchy themes name roles by meaning and surface—palette, bar, popups, notifications, menu, spacing, typography—and standardize normal, hover/keyboard-cursor, focus, selected, and pressed states ([theming design](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/docs/theming.md), [default shell tokens](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/default/themed/shell.toml.tpl)). Rashell should expand its amber-on-black theme into a small semantic token set and shared primitives. This is more valuable than copying any particular Omarchy colors, borders, or glyphs.

6. **Proportional, non-blocking feedback.** Omarchy uses a click-through, non-focus-stealing OSD for continuous adjustments and actionable toasts for completed or exceptional events ([OSD source](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/shell/plugins/osd/Osd.qml), [notification behavior](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/docs/notifications.md)). Rashell should borrow the grammar: OSD for volume/brightness-like changes; short confirmations for discrete actions; persistent UI only when the user must decide something. Owning the full freedesktop notification daemon, history, and DND is a separate product decision, not a prerequisite.

### Borrow selectively

- **Contextual controls:** Omarchy hides unavailable hardware/actions and shows active modes only when meaningful ([toggle behavior](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/13-toggles-idle-screensaver.md)). Rashell should derive visibility from capability/state, but avoid a general shell-expression guard system.
- **Secondary click and scroll shortcuts:** Omarchy assigns many left/right/middle/scroll actions and explicitly notes that users miss them ([top-bar interaction table](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/05-the-top-bar.md)). Rashell may use scroll for naturally continuous controls such as volume, but primary actions need visible panels, tooltips, or searchable commands; hidden gestures must remain accelerators.
- **Inline composition config:** Omarchy keeps ordered bar entries and their settings together in one canonical file ([shell configuration](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/docs/omarchy-shell.md)). That shape is simple and relevant, but Rashell should not build UI mutation, drag persistence, multiple instances, or migration machinery before users need them.

## Deliberately do not copy

- **Distro lifecycle UI:** Omarchy's root menu includes Setup, Install, Remove, Update, defaults, packages, services, security, firmware, and release channels ([first-party menu data](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/default/omarchy/omarchy-menu.jsonc)). Those are Omarchy distribution responsibilities. Rashell should expose shell-owned appearance and behavior only.
- **Hyprland policy and application workflow ownership:** Omarchy specifies tiling layouts, workspace/group/scratchpad behavior, default apps, and a large application hotkey vocabulary ([navigation](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/04-navigation.md)). Rashell may display and invoke compositor state, but Hyprland configuration should remain the source of truth for window-management policy and app bindings.
- **Whole-system theming:** Omarchy retints terminals, editors, browsers, Hyprland, boot UI, and hardware alongside shell surfaces ([theme activation](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/docs/theming.md)). Rashell should theme only its own surfaces and export tokens if useful; it should not become a dotfiles/theme orchestrator.
- **A plugin marketplace or replacement-shell framework:** Omarchy supports git-installed unsandboxed plugins, hot reload, full-bar replacement, enable/disable flows, updates, and review warnings ([plugin model](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/docs/omarchy-shell.md)). Rashell's manifests can organize trusted built-ins, but distribution, remote installation, compatibility promises, and arbitrary full-bar replacement are YAGNI.
- **The bundled utility suite:** unified clipboard semantics, reminders, capture/transcode/share pipelines, package management, lock/polkit, and notification history are genuine Omarchy features, but they are separate products or OS integration concerns rather than requirements for a coherent bar-and-panels shell ([clipboard](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/08-unified-clipboard-history.md), [capture](https://github.com/basecamp/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/manual/12-screenshots-recording.md)).

## Consequence for Rashell's first coherent milestone

Keep the milestone narrow: one multi-monitor three-zone bar with a truly anchored center; workspaces, clock, and contextual system status; one polished audio task panel; a shared keyboard/pointer focus model; semantic theme primitives; shell IPC/action routing; and a small volume OSD. Defer the general menu, notification-daemon ownership, visual layout editing, and third-party plugin lifecycle until the core interaction grammar is proven.
